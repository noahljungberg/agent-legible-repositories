\title{Agent-Legible Repositories:\ Harness Engineering Patterns for AI-Native Software Development}
\author{Noah}
\date{May 2026; revised October 2026}

\begin{document}
\maketitle

\begin{abstract}
AI coding agents are increasingly capable of producing, testing, reviewing, and maintaining software, yet their effectiveness varies sharply across repositories. This paper argues that the repository itself should be treated as the primary agent interface. Documentation, architecture rules, execution plans, tests, scripts, and quality ledgers are not auxiliary artifacts; they are the control surface through which agents perceive and modify software systems. Drawing on recent work in harness engineering, software-engineering benchmarks, agent-computer interfaces, context engineering, skill libraries, token-efficiency research, and multi-agent coordination, this paper defines the \emph{agent-legible repository}: a repository whose structure allows an AI coding agent to localize context, obey project constraints, implement bounded changes, verify behavior, and preserve durable knowledge across sessions. This revision adds a second premise: the repository is no longer edited by one agent at a time. It is a shared, moving workspace that many concurrent agents change while any one of them works, and that humans increasingly steer by reviewing intent rather than reading code. The paper proposes the Agent-Legible Repository framework, a practical design method for creating or repairing repositories intended for mostly or fully AI-written code, including repository-level conventions that make concurrent agent work legible on top of ordinary Git.
\end{abstract}

\section*{Agent-Facing Summary}
This paper is meant to be fed to future coding agents. The operational claim is simple: \textbf{design the repository as the agent's interface}. A good agent-first repository gives the agent a small map, a navigable knowledge base, component contracts, one source of task truth, mechanical architecture rules, cheap verification commands, and a durable ledger of quality and decisions. Do not rely on chat history, human memory, or one giant instruction file. Put durable knowledge in versioned files, keep it indexed, and turn repeated failures into tests, lints, scripts, or docs.

\textbf{Assume you are not alone.} Other agents are probably changing this repository while you work. Treat everything you read as a snapshot that may already be stale. Before you write, find out what is in flight and declare what you will touch. Before you finish, re-sync with the trunk and verify the \emph{integrated} result, not only your branch. Leave a short record of intent and evidence, because the humans steering the repository review intent and evidence, not every line.

\section{Introduction}
Large language model coding agents have moved from code-completion tools toward interactive software workers: they inspect files, run commands, edit code, execute tests, and iterate on failures. Their success, however, is not determined by model capability alone. The same model can behave sharply differently depending on whether the repository provides a coherent operating environment.

The practical lesson from harness engineering is that humans increasingly design environments, feedback loops, and constraints while agents execute implementation work \cite{lopopolo2026harness}. In this setting, repository design becomes a form of interface design. If important knowledge lives in chat threads, private memory, stale wiki pages, or unindexed documents, the agent cannot reliably use it. If architecture is described only as preference rather than enforced as a check, agents will eventually drift. If tasks are broad and verification is expensive, agents spend context on rediscovery and cleanup rather than progress.

This paper proposes a compact framework for repositories meant to support AI-native software development. The framework is intentionally practical: it is meant to become a reusable skill for future agents that create new repositories or repair old ones.

\subsection{What Changed Since the First Draft}
The first draft of this paper (May 2026) implicitly assumed one agent working in one repository at a time, with a human who still read the resulting code. Both assumptions have weakened quickly.

\textbf{Concurrency is the default.} In the author's own practice, ten or more agents working on one repository at the same time is ordinary. At organizational scale, Anthropic reports that merged changes grew from about 2,500 per day in May 2026 to over 30,000 per day by September 2026, and that ``coding is no longer the bottleneck''; the bottleneck became ``all of the developer infrastructure built for human scale: source control, builds, and CI'' \cite{anthropic2026scion}. Empirical studies of public repositories find that concurrent agent pull requests are already common and conflict often \cite{xu2026agentprs,ogenrwot2026agenticflict}.

\textbf{Humans read intent, not code.} Writing code by hand stopped being necessary first; reading every line is following. Anthropic's source-control team reports that its engineers ``still review every change request'' but ``now examine the intent of the change as opposed to reading every line of code'' \cite{anthropic2026scion}. Mining studies find that most agent-generated pull requests receive no review at all \cite{duma2026reviews}, and some researchers argue that keeping humans as mandatory reviewers of agent-written code is a dead end at agent throughput \cite{monperrus2026endreview}.

These shifts do not invalidate the framework; they raise its stakes. When many agents share one repository, every gap in routing, contracts, and verification is multiplied by the number of agents. When humans no longer read code, the repository's intent layer (contracts, plans, decisions, and change records) becomes the main surface through which humans steer, and it must be kept true by mechanical checks because no human reader will notice when it drifts.

This revision does \emph{not} recommend building a new version control system. Git remains the right substrate for nearly all repositories. The argument is that much of the coordination problem can be addressed by repository design and agent harnesses, provided the repository is honest about what Git does and does not give concurrent agents.

\section{Related Work}
\subsection{Software Engineering as an Agent Benchmark}
SWE-bench established real-world issue resolution as a challenging evaluation setting for language models: tasks require multi-file understanding, long-context reasoning, execution environments, and coordinated edits rather than isolated code generation \cite{jimenez2023swebench}. This benchmark line motivates repository structures that help agents find relevant code and verify changes.

SWE-agent introduced the agent-computer interface (ACI) framing, arguing that language model agents are a new category of computer user and benefit from interfaces designed for their abilities and limitations \cite{yang2024sweagent}. An agent-legible repository extends this idea from terminal commands and editor tools to repository topology itself.

Agentless provides an important counterweight to complex autonomy. It showed that relatively simple localization, repair, and validation workflows can be competitive with more elaborate autonomous systems on software-engineering tasks \cite{xia2024agentless}. This supports bounded task queues and explicit verification loops over vague open-ended agency.

\subsection{Harness Engineering and Repository-Local Knowledge}
OpenAI's harness-engineering account describes a fully agent-generated codebase where the repository knowledge base is treated as the system of record: a short entry map points to structured design docs, execution plans, quality records, generated references, and enforcement tools \cite{lopopolo2026harness}. The article's central instruction, ``give Codex a map, not a 1,000-page instruction manual,'' is a concise statement of progressive disclosure for coding agents.

Codified Context presents a related infrastructure for preserving agent memory in a complex codebase through a hot-memory constitution, specialized agents, and a cold-memory specification knowledge base \cite{vasilopoulos2026codified}. The same distinction appears in repository design: short always-loaded instructions should route agents toward deeper on-demand documents rather than attempting to contain all knowledge.

Spec Kit Agents studies context-grounded agentic workflows and adds read-only discovery hooks plus validation hooks to spec-driven development stages \cite{taghavi2026speckit}. The core lesson is that grounding and validation should be explicit workflow operations, not hoped-for behavior.

\subsection{Context Engineering and Skills}
Structured Context Engineering reports that file-native agents can scale through domain-partitioned context and that format choice matters less than architecture and model capability in some settings \cite{mcmillan2026structured}. This supports the use of ordinary Markdown, LaTeX, code comments, and scripts as long as the repository is navigable and partitioned.

Corpus2Skill argues that agents should navigate hierarchical knowledge rather than merely consume flat retrieval results \cite{sun2026corpus2skill}. CUA-Skill shows that reusable structured skills can improve computer-use agent robustness \cite{chen2026cuaskill}. Li further argues that large flat skill libraries can degrade sharply and that hierarchical routing improves scalability \cite{li2026singleagent}. These findings imply that repository instructions and skill libraries should be indexed, layered, and routed, not dumped into one undifferentiated file.

\subsection{Token Efficiency}
Tokenomics examines where tokens are consumed in agentic software engineering and finds substantial cost in iterative refinement and review \cite{salim2026tokenomics}. SWE-Pruner shows that task-aware context pruning can reduce token use while preserving performance in coding-agent settings \cite{wang2026swepruner}. Agent-legible repositories are a manual, file-native form of task-aware pruning: they reduce rediscovery by telling the agent where to look and what to ignore.

The VoltAgent curated paper list is useful as a living index of recent AI-agent research across memory, tooling, evaluation, workflows, and security \cite{voltagent2026awesome}. Such curated indices are valuable inputs to agent workflow design, but they should be distilled into local operating rules before being used in production repositories.

\subsection{Source Control at Agent Scale}
Anthropic's account of replacing Git for its monorepo is the clearest public statement that source control built for human scale becomes a bottleneck under agent load \cite{anthropic2026scion}. The diagnosis is precise: the organization was ``using git as a centralized system with one authoritative copy, but nearly all of our clients were agents and jobs that are online by definition,'' so the properties that make Git excellent for offline, distributed work were undermining scale. The resulting system, Scion, assumes always-online clients, moves history, merges, and commit creation to the server, makes commits cheap, incremental, and lock-free, and treats the working copy as optional and sparse.

Three of its workflow conclusions matter beyond very large monorepos. First, ``a proper merge queue \ldots\ doesn't make much sense at agent scale''; the team could not replicate a global repository lock on the merge queue and instead invested in post-merge and pre-deploy automated testing, accepting that concurrent changes conflict because agents can usually resolve conflicts quickly. Second, review tooling expresses semantic constraints on approvals, distinguishing comment-only changes from sensitive logical changes so that human attention goes to the most consequential work. Third, engineers' role often became to tell agents ``no'' when they violated core system constraints, for example by linearly reading the commit log instead of asking the code review tool.

The authors are explicit that Scion ``is by no means a suitable replacement for git for general use'' and that its ideas only make sense for enormous monorepos, while anticipating that ``this class of problems will become more commonplace over the next six to 12 months'' \cite{anthropic2026scion}. This paper takes that stance seriously: most teams should not build source control, but they should design repositories as if the coordination problems Scion addresses are arriving.

\subsection{Multi-Agent Coordination in Shared Repositories}
CooperBench gives a direct measurement of the coordination problem: when two agents implement separate but potentially colliding features, success is on average about 30\% lower than when one agent performs both tasks, a pattern the authors call the curse of coordination \cite{khatua2026cooperbench}. Its failure modes are instructive for repository design: communication channels fill with vague or inaccurate messages, agents deviate from their own commitments, and agents hold wrong beliefs about each other's plans.

Mining studies show the problem is already present in public repositories. AgenticFlict replays merges for more than 107{,}000 agent-authored pull requests and finds textual conflicts in 27.67\% of them \cite{ogenrwot2026agenticflict}. Xu et al.\ find co-active agent pull requests in 40.2\% of the repositories they study, with textual conflict rates of 41.7\% for cross-agent pairs versus 19.8\% for same-agent pairs; most conflicted files are source code rather than dependency manifests \cite{xu2026agentprs}. A follow-up finds that, in a stratified sample, 47.3\% of textual conflicts occurred even though the two pull requests authored disjoint file sets, because each diff is measured against its own base while the merge is checked against the common merge base. The same work notes that exact local merge replay is cheap and concludes that teams should simply verify mergeability when replay is cheap \cite{subramanian2026lineage}.

Several systems explore where coordination should happen. NP-Bench treats coordination as scheduling: partitioning work into disjoint declared scopes and ordering merges along producer-to-consumer dependencies raised clean integration from 1 of 9 to 9 of 9 scenarios in its benchmark, and the benefit did not shrink with stronger models \cite{muku2026npbench}. Claim Plane studies deterministic pre-write admission over declared change intents and finds large reliability gains, but mostly by serializing work; dynamic admission failed when declared scopes were incomplete \cite{nikolaev2026claimplane}. Cohesion-aware partitioning builds dependency graphs, isolates structural hub files, and partitions along cohesive communities, improving pass rate, speed, and cost over file-based parallel baselines \cite{yang2026cocoder}. STORM argues that isolating each agent in its own worktree only postpones conflicts to an expensive merge, and that mediating writes to a shared workspace works better \cite{liu2026storm}. CodeCRDT shows that conflict-free replicated data types can eliminate textual merge failures but still leave semantic conflicts \cite{pugachev2025codecrdt}.

Practitioner evidence points the same way. Anthropic's parallel-agent compiler experiment used no orchestrator: each agent claimed work by committing a lock file under a \texttt{current\_tasks/} directory, used Git synchronization to resolve races, kept progress notes in the repository because every fresh agent starts without context, and depended on a test verifier that had to be nearly perfect; when all agents converged on one monolithic task they overwrote each other's fixes until the work was re-partitioned \cite{carlini2026compiler}. Current harnesses provide shared task lists with file-locked claiming, inter-agent messaging, and completion hooks, and their documentation still warns that two agents editing the same file leads to overwrites and that work should be split so each agent owns a different set of files \cite{anthropic2026agentteams}.

Finally, stale context is a per-agent version of the same problem. CORVUS shows that agent trajectories accumulate stale file snapshots as files change and that re-injecting current file contents reduces tokens while keeping pass rates comparable \cite{zheng2026corvus}. EA-Graph shows that prose notes can preserve a conclusion while losing the program state that justified it, and that anchoring verification claims to the artifacts they depend on improves judgments after upstream drift \cite{hsu2026eagraph}.

\subsection{Review of Agent-Authored Changes}
Review is shifting from reading diffs to checking intent and evidence. Most agent-generated pull requests in public repositories receive no review, and the reviews that do occur are often performed by other agents, with human involvement appearing as steering \cite{duma2026reviews}. Agent pull request descriptions are not always trustworthy: in one study, 1.7\% of agent pull requests showed high message-code inconsistency, most often describing changes that were never implemented, and those pull requests had much lower acceptance (28.3\% versus 80.0\%) and took about 3.5 times longer to merge \cite{gong2026mci}. Monperrus argues that agents can serve every stated goal of code review at lower cost and that keeping humans as mandatory reviewers of agent-written code neither provides meaningful assurance nor scales \cite{monperrus2026endreview}. The repository-design implication is not to remove humans but to give them a smaller, truer surface: declared intent, scope, and mechanically checkable evidence.

\section{Problem Statement}
A repository that works for human experts can still be hostile to AI agents. Common failure modes include:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Context blindness}: the agent cannot find the relevant files, conventions, or prior decisions.
  \item \textbf{Instruction overload}: one large instruction file crowds out task context and makes priority unclear.
  \item \textbf{Architectural drift}: dependencies, naming, ownership, and layering are described but not checked.
  \item \textbf{Repeated rediscovery}: each session spends tokens re-learning the same layout and decisions.
  \item \textbf{Task overbreadth}: agents attempt broad refactors instead of completing one bounded change.
  \item \textbf{Verification friction}: tests, builds, linters, or acceptance checks are missing, slow, undocumented, or flaky.
  \item \textbf{Documentation rot}: docs are not versioned with the code or lack ownership and freshness checks.
  \item \textbf{Chat-memory dependency}: critical knowledge lives in conversations that future agents cannot access.
\end{enumerate}

Concurrent agent work adds five more:

\begin{enumerate}[leftmargin=*,resume]
  \item \textbf{Stale worldview}: an agent reasons from files, plans, or test results that other agents have already changed.
  \item \textbf{Invisible intent}: in-flight work lives in private branches and context windows, so agents cannot see or avoid each other's plans.
  \item \textbf{Semantic collision}: changes merge cleanly as text but break together, because each was verified only against its own base.
  \item \textbf{Contention hotspots}: shared files that every task touches (one plan file, one changelog, one registry, one index) serialize work and generate conflicts.
  \item \textbf{Unreviewable volume}: change volume exceeds human reading capacity, and change descriptions are not reliably tied to evidence.
\end{enumerate}

The design objective is not to maximize documentation volume. It is to maximize \emph{agent navigation quality}: the probability that an agent reads the right context, ignores irrelevant context, makes a bounded edit, and verifies the result. Under concurrency, the objective extends to \emph{integration quality}: the probability that many bounded edits, made in parallel, still compose.

\section{Definitions}
\textbf{Agent-legible repository.} A repository whose local artifacts let an AI coding agent understand what to do, where to look, which constraints apply, how to verify work, and how to update durable project memory.

\textbf{Entry map.} A short always-loaded file, often named \texttt{AGENTS.md}, \texttt{CLAUDE.md}, \texttt{GEMINI.md}, Cursor rules, Copilot instructions, or another tool-specific equivalent, that describes the repository purpose, workflow, key commands, and pointers to deeper documents. The filename is less important than the role: the file is a maintained routing map into deeper context.

\textbf{Cold memory.} Versioned on-demand documents such as architecture docs, component design docs, product specs, security notes, and references.

\textbf{Hot memory.} Short high-priority operating rules that should be loaded every session: current task protocol, conventions, verification commands, and recovery steps.

\textbf{Component contract.} A design document for one component that records purpose, public API, implementation files, dependencies, tests, constraints, and non-goals.

\textbf{Execution plan.} A versioned task queue with checked tasks, acceptance criteria, decision log, and progress log.

\textbf{Verification harness.} The set of commands, tests, linters, scripts, probes, and acceptance checks that let an agent decide whether a change is complete.

\textbf{Concurrent repository.} A repository that multiple agents modify at overlapping times, so that any agent's view of the trunk can become stale during its own task.

\textbf{Work claim.} A visible, short-lived declaration that an agent is working on a task, with the scope it expects to touch (paths, interfaces, generated outputs), released when the work merges or is abandoned.

\textbf{Contention hotspot.} A file or interface that many unrelated tasks must change, such as a central registry, a single progress log, a hub module, or a shared public contract.

\textbf{Intent record.} The short statement attached to a change (commit message, pull request description, or plan entry) that says what the change is for, what it touched, and which verification evidence supports it.

\textbf{Integration verification.} Verification run against the change combined with the current trunk, as opposed to verification of the branch in isolation.

\section{The Agent-Legible Repository Framework}
The framework consists of eleven mutually reinforcing artifacts. The first nine make a repository legible to one agent; the last two make it legible to many agents working at once.

\subsection{Entry Map}
The entry map should be concise. It answers: What is this repo? What is the current workflow? What commands verify work? Where are architecture, conventions, design docs, active plans, and known issues? It should not duplicate every component detail. In a concurrent repository it should also state the concurrency model in a few lines: that other agents may be editing, where in-flight work is visible, how to claim work, and how to verify against the current trunk.

\subsection{Knowledge Topology}
The repository needs an indexed knowledge base. A typical layout is:

\begin{verbatim}
AGENTS.md
ARCHITECTURE.md
CONVENTIONS.md
docs/
  design/
    index.md
    component-a.md
    component-b.md
  plans/
    active/          # one file per task; carries the work claim
    completed/
  decisions/         # one file per decision
  references/
  examples/
  QUALITY.md
  known-issues/      # one file per issue, or a generated index
src/
tests/
scripts/
\end{verbatim}

The index is critical. Without an index, many docs become an unsearchable pile. The agent should learn the reading path from the repository itself.

The layout is also a concurrency decision. Knowledge that every task appends to (a single progress log, a single decisions file, a hand-maintained changelog) becomes a contention hotspot when many agents run at once. Prefer one file per plan, decision, issue, or change note, and generate indices and changelogs from those files with a script instead of editing them by hand. Small, separately owned files merge cleanly; one shared file does not.

\subsection{Component Contracts}
Each major component should have one component design document. For example, a systems repository might have \texttt{docs/design/loader.md}, \texttt{docs/design/memory-reader.md}, and \texttt{docs/design/overlay.md}; a web service might have \texttt{docs/design/auth.md}, \texttt{docs/design/billing.md}, and \texttt{docs/design/api.md}. These files are not ordinary explanatory docs. They are context routers. When an agent is asked to work on a component, it should read that component's design doc first instead of scanning the whole repository.

Each component contract should include purpose, allowed dependencies, public API, implementation files, test files, constraints, acceptance criteria, and explicit non-goals. This localizes context. If the task is about the billing adapter, the agent should not need to understand every renderer, database adapter, or deployment script. If a component has no design doc, the agent should treat that as missing harness infrastructure and either create a minimal contract or record the gap before doing broad work.

Under concurrency, component contracts are also coordination boundaries. A contract that names the paths a component owns, the consumers of its public API, and the hub files it shares with other components lets agents partition work along cohesive boundaries instead of arbitrary file lists \cite{yang2026cocoder}. A change to a public contract is a producer-to-consumer event: it should be scheduled and merged before dependent work, not discovered at merge time \cite{muku2026npbench}.

\subsection{Active Execution Plans}
Large work should be decomposed into checkable tasks. The plan should identify the next unchecked item, define acceptance criteria, and require the agent to update progress only after verification. This converts vague intent into an executable queue. With many agents, keep one plan per task or workstream rather than one shared plan that every agent edits.

\subsection{Mechanical Invariants}
Documentation alone is weak. Important rules should become mechanical checks: dependency boundaries, naming conventions, public API documentation, file size limits, schema validity, generated-code freshness, forbidden imports, and required tests. Lint errors should include remediation guidance because their output becomes agent context.

Mechanical invariants are also how human judgment scales across concurrent agents. When an engineer has to tell an agent ``no'' because it violated a system constraint \cite{anthropic2026scion}, that refusal should be encoded once, as a lint, test, contract non-goal, or anti-pattern, so that the next ten agents do not need to hear it again.

\subsection{Verification Harness}
Every repository should expose a small set of commands for build, test, lint, typecheck, formatting, and domain-specific acceptance. The commands should be documented in the entry map and kept cheap enough to run frequently. When possible, scripts should encapsulate complex validation instead of requiring agents to remember command sequences. Verification output should be short and greppable, with details in log files, because the output becomes agent context; offering a fast, sampled mode helps agents that cannot judge elapsed time \cite{carlini2026compiler}.

\subsection{Quality and Entropy Ledger}
A quality ledger records component trust levels, test gaps, known risks, and last-updated dates. A known-issues file records non-blocking defects. These files prevent agents from treating all parts of the codebase as equally reliable.

\subsection{Examples and Anti-Patterns}
Agents imitate local examples. Repositories should include gold-standard examples and explicit anti-patterns for common mistakes. When a recurring failure appears, either add a test/lint or document it as an anti-pattern with a replacement pattern.

\subsection{Skill Layer}
The repository should have reusable skills for repeated workflows: adding a component, writing a design doc, performing a code review, debugging a failing test, creating a migration, or auditing documentation. Skills should be hierarchical and specific. A flat list of dozens of similar skills creates selection burden.

\subsection{Coordination Surface}
A concurrent repository needs one visible place where in-flight work is declared. If all agents share a harness with a task list and file-locked claiming, use it \cite{anthropic2026agentteams}. If agents share only the repository, commit a small claim file per task, for example the header of the task's file in \texttt{docs/plans/active/}, stating the task, the claiming session, the expected scope (paths, public interfaces, generated outputs), and when it started. Pushing a new claim to the trunk is an atomic test: if another agent already claimed the task, the push fails and the second agent picks other work \cite{carlini2026compiler}.

Claims are coordination hints, not locks on the whole repository. They let agents avoid duplicate work and predictable collisions, and they make intent visible to the next agent. They should be amended when scope grows and removed when the work merges or is abandoned. Overly broad or incomplete claims either serialize everything or fail closed \cite{nikolaev2026claimplane}.

\subsection{Intent Records}
Every merged change should carry a short intent record: what the change is for, which component and contract it touches, what it deliberately does not do, and which commands were run with which results. Intent records are the surface that humans review when they no longer read every line \cite{anthropic2026scion}, and the surface that later agents read to understand why the code is the way it is. Because change descriptions can claim work that was never implemented \cite{gong2026mci}, intent records should point to evidence a machine can re-check (test names, command output, CI runs) rather than narrative assurances.

\section{Designing for Concurrent Agents}
\subsection{Three Layers of Concurrency Control}
Coordination among concurrent agents is not one problem owned by one tool. It is split across three layers, and a repository designer should know which layer owns which part.

\begin{table}[h]
\centering
\small
\begin{tabularx}{\textwidth}{l L L}
\toprule
Layer & Owns & Examples \\
\midrule
Repository & Durable, versioned coordination knowledge: boundaries, contracts, claims, intent records, invariants, and verification commands. & Component contracts with owned paths; per-task plan files; generated indices; lints; integration checks. \\
Harness & Live, session-level coordination: isolation, task assignment, messaging, permissions, and completion gates. & Worktrees or containers per agent; shared task lists with locked claiming; inter-agent messages; task-completion hooks \cite{anthropic2026agentteams}. \\
Source control and forge & Storage, history, merging, review, and testing of changes at scale. & Server-side merges, cheap commits, sparse checkouts, post-merge testing, semantic approval rules \cite{anthropic2026scion}. \\
\bottomrule
\end{tabularx}
\caption{Where concurrency problems are solved. This paper addresses the repository layer and assumes the other two.}
\end{table}

For most teams, the honest assessment is that the source-control layer is a real bottleneck at high agent counts, that the harness layer is improving quickly and absorbs much of the live coordination, and that the repository layer is the one a team fully controls today. The repository layer is also the only one that survives a change of harness.

\subsection{What Git Does and Does Not Give Concurrent Agents}
Git gives every agent an isolated, complete, cheap-to-branch snapshot and a reliable three-way merge. Those are real strengths: isolation prevents agents from overwriting each other mid-task, and pushing to a shared trunk is an atomic compare-and-swap that can arbitrate simple claims.

Git does not give agents awareness. A branch hides in-flight intent until it is pushed and merged. A clone or worktree is stale from the moment it is created. A clean textual merge says nothing about semantic compatibility, and conflicts can arise even when two changes authored disjoint files \cite{subramanian2026lineage}. Global serialization through a merge queue does not keep up at agent scale \cite{anthropic2026scion}. And isolation postpones conflicts rather than removing them \cite{liu2026storm}. The design rules below compensate for these gaps without replacing Git.

\subsection{Design Rules}
\begin{enumerate}[leftmargin=*]
  \item \textbf{Assume a moving trunk.} Tell agents in the entry map that the repository is concurrent. Agents should re-read a file before editing it if time has passed, re-sync before declaring work done, and treat earlier test results as stale once the trunk moves \cite{zheng2026corvus,hsu2026eagraph}.
  \item \textbf{Declare scope before writing.} Every nontrivial task gets a claim with expected scope. Agents check existing claims before starting and amend their own when scope grows.
  \item \textbf{Partition along cohesion, not file counts.} Use component contracts to assign work to cohesive components. Identify hub files and shared public contracts explicitly; changes to them are scheduled, merged first, and announced, because they are where parallel work collides \cite{yang2026cocoder,muku2026npbench}.
  \item \textbf{Shard shared knowledge.} Replace append-everywhere files with one file per plan, decision, issue, or change note. Generate indices, registries, and changelogs by script. Regenerate lockfiles and generated code with project tooling instead of merging them by hand.
  \item \textbf{Keep changes small and short-lived.} Small changes that integrate often have less time to go stale and smaller conflict surfaces. Long-running branches are the main source of expensive merges.
  \item \textbf{Verify the integrated result.} A branch that passes its own tests is not done. Replay the merge against the current trunk (local merge replay is cheap \cite{subramanian2026lineage}), re-run affected verification, and rely on post-merge and pre-deploy checks to catch semantic collisions that no pre-merge gate will see \cite{anthropic2026scion,khatua2026cooperbench}.
  \item \textbf{Review intent and evidence, and route attention by risk.} Require intent records. Use path-based ownership or approval rules to separate low-risk changes (comments, docs, tests) from sensitive ones (public contracts, security boundaries, migrations) so that scarce human attention goes where it matters.
  \item \textbf{Encode every ``no'' once.} When a human or reviewing agent rejects a pattern, turn the rejection into a lint, test, contract non-goal, or anti-pattern so it applies to all concurrent agents.
\end{enumerate}

\subsection{What Not To Do}
Do not build a version control system unless the repository is genuinely at the scale where storage and transfer dominate; the teams that have done so say it only makes sense for enormous monorepos \cite{anthropic2026scion}. Do not try to solve coordination by serializing everything through one lock, one plan file, or one merge queue; that recovers correctness by giving up the parallelism that motivated running many agents \cite{nikolaev2026claimplane}. Do not let agents communicate only through free-form chat; vague, unkept, or misread messages are a primary coordination failure \cite{khatua2026cooperbench}. Prefer durable, structured, verifiable state: claims, contracts, intent records, and checks.

\section{Operational Method}
\subsection{Greenfield Setup}
For a new repository, create the harness before the code grows:

\begin{enumerate}[leftmargin=*]
  \item Write a short agent entry file, such as \texttt{AGENTS.md} or a tool-specific equivalent, with purpose, workflow, commands, document map, and concurrency model.
  \item Define architecture layers and dependency rules in \texttt{ARCHITECTURE.md}.
  \item Define coding conventions and error-handling patterns in \texttt{CONVENTIONS.md}.
  \item Create \texttt{docs/design/index.md} before writing many component docs.
  \item For each major component, write one component design doc before or alongside implementation, including owned paths and consumers of its public API.
  \item Add tests and scripts as soon as public APIs exist, including a command that verifies a branch against the current trunk.
  \item Use one plan file per task in \texttt{docs/plans/active/}, with a claim header, and require one-task-at-a-time execution per agent.
  \item Track quality, known issues, and decisions in versioned files, one entry per file where many agents will write.
  \item Define the intent-record format for commits or pull requests.
\end{enumerate}

\subsection{Brownfield Repair}
For an existing repository, do not begin by documenting everything. Begin by reducing agent uncertainty:

\begin{enumerate}[leftmargin=*]
  \item Inventory components and current verification commands.
  \item Create or repair the entry map.
  \item Create an architecture map from actual imports and build targets.
  \item Create a design index with statuses: complete, in progress, stale, missing.
  \item Write component contracts only for high-change, high-risk, or frequently edited areas first.
  \item Add scripts for the commands humans already run manually.
  \item Add mechanical checks for the most damaging recurring mistakes.
  \item Create a quality ledger and known-issues file.
  \item If several agents already work in the repository, find the contention hotspots (files most often involved in conflicts or touched by unrelated changes) and shard, generate, or schedule them first.
\end{enumerate}

\subsection{Default Agent Protocol}
A future coding agent should follow this loop:

\begin{enumerate}[leftmargin=*]
  \item Sync with the current trunk.
  \item Read the entry map.
  \item Read the active plan or issue, and check existing claims for overlapping work.
  \item Identify the component and read its design contract.
  \item Claim the task with its expected scope, unless the harness already assigned it.
  \item Read architecture and conventions relevant to the change.
  \item Inspect existing code and tests in the target component.
  \item Make the smallest change satisfying the task. Re-read any file before editing it if others may have changed it.
  \item Run the documented verification commands.
  \item Re-sync with the trunk, resolve conflicts, and re-run affected verification on the integrated result.
  \item Write the intent record with evidence; update docs, plan, quality ledger, or known issues only when the result changes durable project knowledge.
  \item Release the claim and stop after the requested task is complete.
\end{enumerate}

\section{Evaluation Metrics}
Agent-legibility can be evaluated empirically. Useful metrics include:

\begin{itemize}[leftmargin=*]
  \item \textbf{Context localization}: files opened before first correct edit; irrelevant files opened per task.
  \item \textbf{Token efficiency}: input tokens before first edit; total tokens to green verification.
  \item \textbf{Task success}: percentage of tasks completed without human clarification.
  \item \textbf{Verification success}: first-run build/test pass rate after edit; time-to-green.
  \item \textbf{Architectural coherence}: number of dependency or convention violations per task.
  \item \textbf{Recovery}: ability to resume from a fresh session using only repository-local state.
  \item \textbf{Documentation freshness}: stale links, stale file references, and docs contradicted by code.
  \item \textbf{Mistake recurrence}: repeated failures before and after adding docs, lints, or scripts.
\end{itemize}

For concurrent repositories, add:

\begin{itemize}[leftmargin=*]
  \item \textbf{Conflict rate}: share of changes that conflict with the trunk at integration time, and which files cause them.
  \item \textbf{Semantic breakage}: post-merge failures in changes that each passed pre-merge verification.
  \item \textbf{Duplicate and overlapping work}: tasks attempted by more than one agent, or claims with overlapping scope.
  \item \textbf{Serialization ratio}: share of work that had to wait on another agent; parallel speedup relative to one agent.
  \item \textbf{Intent fidelity}: share of intent records whose claims match the diff and the cited evidence.
  \item \textbf{Human attention}: share of changes that required human review, and whether that share tracks risk.
\end{itemize}

A practical experiment is to run the same set of coding tasks against two versions of a repository: baseline and agent-legible. Compare task success, tokens, files opened, verification failures, and human interventions. For concurrency, run the same task set with one agent and with several agents in parallel, and compare integrated success, conflicts, and wall-clock time.

\section{Limitations}
The framework is model-dependent. A structure that works well for frontier coding agents may be insufficient for smaller models. Documentation can also become a liability if stale, too broad, or not connected to mechanical checks. Small prototypes may not need the full framework. Some domains require additional artifacts, such as threat models, product specs, data schemas, migration guides, or UI design systems. Finally, this paper is a framework and working synthesis; formal validation requires controlled experiments across repositories, models, and task types.

The concurrency guidance carries additional caveats. Much of the 2026 evidence on multi-agent coordination comes from single groups, recent preprints, or self-built benchmarks, and should be read as early. Claims can become their own bottleneck if they are too coarse, and incomplete claims can block legitimate work. Harness capabilities for coordination are changing quickly, so a repository should depend on the repository-layer conventions here rather than on any one harness feature. Finally, reviewing intent instead of code is only as safe as the evidence behind the intent; it depends on strong verification and post-merge checks.

\section{Conclusion}
AI-native software development changes the role of repository design. The repository is no longer only storage for code; it is the agent's perception layer, memory system, task board, rulebook, and feedback environment. It is also, increasingly, a shared workspace that many agents change at once and that humans steer through intent rather than through reading code. Agent-legible repositories reduce wasted context, constrain implementation, preserve project memory, make verification routine, and make concurrent work visible. The core prescription is simple: give agents a map, make knowledge navigable, enforce what matters mechanically, declare work before doing it, verify the integrated result, and feed every recurring failure back into the harness.

\section{Agent Consumption Checklist}
When using this paper as context, extract the following operational requirements:

\begin{enumerate}[leftmargin=*]
  \item Create or repair a short entry map.
  \item Create indexed cold memory under \texttt{docs/}.
  \item Give every major component a contract.
  \item Use active execution plans for multi-step work.
  \item Make architecture and conventions mechanically checkable where possible.
  \item Keep verification commands obvious and runnable.
  \item Maintain quality, known-issue, and decision ledgers.
  \item Convert repeated failures into docs, tests, lints, scripts, or skills.
  \item Assume concurrent agents: state the concurrency model, re-sync before finishing, and treat earlier reads as stale.
  \item Declare scope with a claim before writing; check claims before starting.
  \item Shard or generate contention hotspots; never hand-merge generated files.
  \item Verify the integrated result against the current trunk, not only the branch.
  \item Attach an intent record with re-checkable evidence to every change.
\end{enumerate}

\section{Minimal Component Contract Template}
\begin{verbatim}
# Design: <Component Name>

## Purpose
What this component owns and why it exists.

## Public API
Headers, exported functions/classes, schemas, CLI commands, or routes.

## Implementation Files
Files owned by this component and what each does.

## Dependencies
Allowed dependencies and forbidden dependencies.

## Consumers And Shared Files
Components that depend on this API. Hub or shared files that changes
here also touch. Changes to the public API are scheduled first.

## Constraints
Performance, security, style, error handling, platform, file-size rules.

## Tests
Unit, integration, acceptance, fixtures, mocks.

## Non-Goals
What future agents should not implement here.

## Status
Planned / In progress / Complete / Needs update.
\end{verbatim}

\section{Minimal Claim and Intent Record Templates}
A claim, placed at the top of a task file in \texttt{docs/plans/active/} or kept in the harness task list:

\begin{verbatim}
---
task: <short task name>
claimed-by: <agent or session identifier>
started: <date and time>
scope:
  paths: [<paths this task expects to change>]
  interfaces: [<public APIs or contracts it may change>]
  generated: [<generated outputs it will regenerate>]
status: claimed | in-review | merged | abandoned
---
\end{verbatim}

An intent record, used as a commit message body or pull request description:

\begin{verbatim}
Intent: <one sentence: what this change is for>
Component: <component and contract touched>
Scope: <what changed>; Not changed: <deliberate non-goals>
Contract change: none | <API change and affected consumers>
Evidence: <commands run against trunk at <commit>, with results>
Risk: low (docs/tests/comments) | normal | sensitive (<why>)
\end{verbatim}
