\title{Agent-Legible Repositories:\ Harness Engineering Patterns for AI-Native Software Development}
\author{Noah}
\date{May 2026; revised October 2026}

\begin{document}
\maketitle

\begin{abstract}
AI coding agents are increasingly capable of producing, testing, reviewing, and maintaining software, yet their effectiveness varies sharply across repositories. This paper argues that the repository itself should be treated as the primary agent interface. Documentation, architecture rules, execution plans, tests, scripts, and quality ledgers are not auxiliary artifacts; they are the control surface through which agents perceive and modify software systems. This paper defines the \emph{agent-legible repository}: a repository whose structure allows an AI coding agent to localize context, obey project constraints, implement bounded changes, verify behavior, and preserve durable knowledge across sessions. This revision adds a second premise: the repository is no longer edited by one agent at a time. It is a shared, moving workspace that many concurrent agents change while any one of them works, and that humans increasingly steer by reviewing intent and evidence rather than reading code. Because the field changes in months, the revision weights evidence explicitly: recent first-party engineering reports from frontier labs and AI-coding companies carry the argument, and older research is treated as background. The paper proposes the Agent-Legible Repository framework, a practical design method for creating or repairing repositories intended for mostly or fully AI-written code, including repository-level conventions that make concurrent agent work legible on top of ordinary Git, and completion gates: harness hooks that require evidence before an agent may finish a task or open a pull request.
\end{abstract}

\section*{Agent-Facing Summary}
This paper is meant to be fed to future coding agents. The operational claim is simple: \textbf{design the repository as the agent's interface}. A good agent-first repository gives the agent a small map, a navigable knowledge base, component contracts, one source of task truth, mechanical architecture rules, cheap verification commands, and a durable ledger of quality and decisions. Do not rely on chat history, human memory, or one giant instruction file. Put durable knowledge in versioned files, keep it indexed, and turn repeated failures into tests, lints, scripts, or docs.

\textbf{Assume you are not alone.} Other agents are probably changing this repository while you work. Treat everything you read as a snapshot that may already be stale. Before you write, find out what is in flight and declare what you will touch. Before you finish, re-sync with the trunk and verify the \emph{integrated} result, not only your branch. Leave a short record of intent and evidence, because the humans steering the repository review intent and evidence, not every line.

\textbf{Expect a gate.} In a well-built repository you cannot finish or open a pull request until the checks pass and your final message states what you verified, what you did not, which history you checked, and how confident you are. Do not weaken tests, checks, or the gate to get through it; report what you could not verify instead.

\section{Introduction}
Large language model coding agents have moved from code-completion tools toward interactive software workers: they inspect files, run commands, edit code, execute tests, and iterate on failures. Their success, however, is not determined by model capability alone. The same model can behave sharply differently depending on whether the repository provides a coherent operating environment.

Humans increasingly design environments, feedback loops, and constraints while agents execute implementation work. In this setting, repository design becomes a form of interface design. If important knowledge lives in chat threads, private memory, stale wiki pages, or unindexed documents, the agent cannot reliably use it; as one recent report puts it, ``Agents can only learn from what they can see'' \cite{anthropic2026slack}. If architecture is described only as preference rather than enforced as a check, agents will eventually drift. If tasks are broad and verification is expensive, agents spend context on rediscovery and cleanup rather than progress.

This paper proposes a compact framework for repositories meant to support AI-native software development. The framework is intentionally practical: it is meant to become a reusable skill for future agents that create new repositories or repair old ones.

\subsection{What Changed Since the First Draft}
The first draft of this paper (May 2026) implicitly assumed one agent working in one repository at a time, with a human who still read the resulting code. Both assumptions have weakened quickly.

\textbf{Concurrency is the default.} In the author's own practice, ten or more agents working on one repository at the same time is ordinary. Frontier organizations report the same shift at much larger scale. Anthropic's merged changes grew from about 2,500 per day in May 2026 to over 30,000 per day by September, and it reports that the bottleneck moved to ``all of the developer infrastructure built for human scale: source control, builds, and CI'' \cite{anthropic2026scion}. Its CI job volume grew 25 times in six months, with Claude authoring 80\% of the code \cite{malhotra2026ci}. GitHub reports 7.38 billion commits in September 2026, more than five times a year earlier, and names merges contending on a single trunk reference as a core bottleneck \cite{celenza2026gitinfra}. OpenAI reports that its weekly pull request volume more than doubled since the fourth quarter of 2025 \cite{srikanth2026reviewrules}. Cursor built its own Git storage system because ``Version control is at the core of all of this, and it is possibly the hardest thing to change overnight'' \cite{marti2026gitscale}. Individual agent sessions also run longer: Anthropic reports that Claude works 3.3 times longer per prompt than in March 2026 \cite{segner2026longsessions}, which gives the trunk more time to move under each task.

\textbf{Humans review intent and evidence, not code.} Writing code by hand stopped being necessary first; reading every line is following. Anthropic's source-control team still reviews every change to its system but now examines ``the intent of the change as opposed to reading every line of code'' \cite{anthropic2026scion}. Its migration playbook says to ``Review loop results, not code'' \cite{anthropic2026migrations}. GitHub frames the question for agent patches as ``can a person validate it?'' \cite{abuadas2026yes}, and Augment Code summarizes its review pipeline as ``Agents do the mechanical work. Humans make the consequential decisions'' \cite{utture2026prmerge}. Decisions that remain human are increasingly explicit: Block leaves ``merges to main and deploys to production up to people'' while agents produce thousands of pull requests \cite{anthropic2026block}.

\textbf{Constraints replace reading.} Robert C. Martin, the author of \emph{Clean Code}, describes the same shift from the practitioner side: ``My current strategy is to not read any of the code written by my agents. \ldots\ What I do instead is to surround the agents with extreme constraints,'' naming unit tests, Gherkin tests, QA procedures, quality metrics, mutation testing, and test coverage \cite{martin2026constraints}. Code quality still matters, but now for the agents' sake: ``Messy code slows my agents down,'' so he constrains ``function sizes, cyclomatic complexity, and test coverage'' \cite{martin2026messy}. Anthropic's Claude Code team reports that ``Most review now happens before a PR exists'' \cite{osmani2026codereview}. The author's own practice is the same: a personal gate, enforced by harness hooks, that does not let an agent finish or open a pull request without evidence. This revision includes a domain-neutral version of that gate as a template.

These shifts do not invalidate the framework; they raise its stakes. When many agents share one repository, every gap in routing, contracts, and verification is multiplied by the number of agents. When humans no longer read code, the repository's intent layer (contracts, plans, decisions, and change records) becomes the main surface through which humans steer, and it must be kept true by mechanical checks because no human reader will notice when it drifts.

This revision does \emph{not} recommend building a new version control system. Anthropic, GitHub, and Cursor have each rebuilt storage and serving layers for agent load \cite{anthropic2026scion,celenza2026gitinfra,marti2026gitscale}, but that is forge and infrastructure work that most teams will consume rather than build. The argument here is that much of the coordination problem can be addressed by repository design and agent harnesses, provided the repository is honest about what Git does and does not give concurrent agents.

\subsection{Evidence Policy}
Agentic software development changes on a timescale of months. A study run on models and harnesses from early 2026 may describe agents two generations behind current practice. This revision therefore weights sources on two axes.

\begin{enumerate}[leftmargin=*]
  \item \textbf{Recency first.} Sources from roughly the quarter before a revision (for this revision, July 2026 onward) carry the argument. Older sources are background: they may illustrate a point or show its history, but no recommendation rests on them alone.
  \item \textbf{Frontier practice second.} First-party engineering reports and documentation from frontier labs (Anthropic, OpenAI) and from AI-coding companies and forges that run current agents at production scale (for example Cursor, Factory, Augment Code, GitHub) rank above academic preprints, which more often evaluate older models on self-built benchmarks. Recent preprints still count as independent corroboration.
\end{enumerate}

Two caveats apply. First-party reports are not peer reviewed, and their authors have a commercial interest in the products they describe; their metrics are self-reported. And recency weighting means this paper will age quickly: each revision should re-run the search and re-weight its sources rather than accumulate them.

\section{Evidence}
This section summarizes the evidence behind the revision, newest and most authoritative first. Section~\ref{sec:background} condenses the older work that shaped the first draft.

\subsection{Source Control and CI at Agent Scale}
Anthropic's account of replacing Git for its monorepo is the clearest statement that source control built for human scale breaks under agent load \cite{anthropic2026scion}. The organization was ``using git as a centralized system with one authoritative copy, but nearly all of our clients were agents and jobs that are online by definition,'' so the properties that make Git excellent for offline, distributed work were undermining scale. The resulting system, Scion, assumes always-online clients, moves history, merges, and commit creation to the server, makes commits cheap, incremental, and lock-free, and treats the working copy as optional and sparse.

Three of its workflow conclusions matter beyond very large monorepos. First, ``a proper merge queue \ldots\ doesn't make much sense at agent scale''; the team asks, ``What does CI even mean when hundreds or even thousands of changes can merge while tests are running?'', and relies on post-merge and pre-deploy automated testing, accepting that concurrent changes conflict because agents can usually resolve conflicts quickly. Second, review tooling expresses semantic constraints on approvals, distinguishing comment-only changes from sensitive logical changes so that human attention goes to the most consequential work. Third, engineers' role often became to tell agents ``no'' when they violated core system constraints, for example by linearly reading the commit log instead of asking the code review tool. The authors state that Scion ``is by no means a suitable replacement for git for general use,'' while anticipating that ``this class of problems will become more commonplace over the next six to 12 months.''

GitHub and Cursor report the same pressure from the forge side. GitHub names four agent-driven bottlenecks: per-agent commit latency (``An agent in a tight loop commits or checkpoints after nearly every action''), write throughput, merges contending on a single reference (``Merges contend on one reference''), and read fan-out from CI; its redesign separates durability from compute and coordinates only the reference update \cite{celenza2026gitinfra}. Cursor describes a Git storage system built on a write-ahead log in object storage, serving millions of small agent repositories \cite{marti2026gitscale}. CI strains in the same way: Anthropic patched its test-selection service three times before redesigning it, found that lag in recording results meant test selection ran on stale data, and advises teams to ``assume your architecture will be at a 25x load within two quarters'' \cite{malhotra2026ci}.

\subsection{Parallel Agents in Practice}
Recent practitioner reports converge on a small set of coordination patterns. Anthropic's field guide to cloud sessions gives each task its own machine and branch, and names the cost of that isolation: one session hit a flaky test that another session was already fixing. Its advice: ``Split parallel tasks along file boundaries, merge the branches in a sensible order, and expect a session to report problems that another session is already fixing.'' It also notes that personal configuration does not reach cloud agents, so ``the repository has to say so'' \cite{osmani2026cloud}. Claude Code documentation adds cross-session messaging so that ``When a change in one session breaks what another is building on, Claude can warn that session before you notice'' \cite{anthropic2026crosssession}, and shared task lists with file-locked claiming for agent teams, while warning that two agents editing the same file leads to overwrites \cite{anthropic2026agentteams}.

At organizational scale, Block's migrations use a planning model that directs up to dozens of worker agents across ``hundreds or thousands of individual pull requests,'' with merges and deploys left to humans \cite{anthropic2026block}. Anthropic's migration playbook keeps a rulebook, a dependency map, and a gap inventory on disk, rebuilds its work queue from disk so runs can resume, uses adversarial reviewers, and routes the most expensive shared operation through one build daemon: ``This serializes the most expensive operation instead of letting multiple agents trigger it independently.'' Its core lesson is ``you don't fix the code. You fix the process (loop) that produced the code'' \cite{anthropic2026migrations}. Cursor's Projects use a coordinator agent that does not write code, a set of shared context files that agents add to so that ``every future agent can use those instructions,'' and a coordinator that ``adds a lint rule whenever it sees the same mistake twice'' \cite{cursor2026projects}. OpenAI's Agents API exposes the same lead-and-subagent structure, where ``Each subagent maintains its own context'' and the main agent coordinates and merges results \cite{openai2026agentsapi}; an OpenAI customer report on a parallel migration found that ``Simpler instructions worked better than a more elaborate setup'' \cite{openai2026asana}.

Factory reports what goes wrong without an explicit standard of completion. On large clean-room rebuilds, a single agent stopped at 36\% parity on one task, believing it was done, while an orchestrator, implementer, and validator system reached 90\%; the validator built an executable check before implementation began. Its diagnosis applies to any team of agents: ``Every local judgment may be reasonable while parts of the whole remain unmeasured'' \cite{factory2026large}. Factory also scores repositories for agent readiness, including whether they have ``a documented, one-line setup command,'' and reports that its multi-agent system works best on repositories at the higher readiness levels \cite{factory2026sandboxes}.

\subsection{Repository Instructions and Context}
Frontier guidance on instruction files has moved toward smaller, routed context. Anthropic removed ``over 80\% of Claude Code's system prompt'' for its current models with no measurable loss on its coding evaluations, and advises: ``Keep your CLAUDE.md lightweight and briefly describe what your repo is for, but spend most of the tokens on gotchas inside of the codebase,'' with deeper material in a tree of files loaded when needed \cite{shihipar2026context}. OpenAI's guidance for its current models is the same: ``make the root document a minimal router that points to supporting docs and scripts,'' because ``Requiring a stack of docs or a full repo map before every edit is excessive for a typo fix,'' and because ``Repository skills also guide other contributors' agents, which may use different models'' \cite{provencher2026astra}. OpenAI's model guide asks that prompts, skills, and repository instructions agree on what counts as done, and that agents end with ``a short handoff covering what changed, what was checked, and what still needs attention'' \cite{openai2026gpt6guide}.

Verification commands belong in the repository: ``A good practice is to list your exact build and test commands in CLAUDE.md so Claude doesn't have to infer them,'' and shared verification skills turn personal checks into ``team infrastructure'' \cite{deoliveira2026verification}. Records of work also become context: OpenAI keeps intent, actions, decisions, and outcomes in one runnable notebook so that each run is findable by the next \cite{lewi2026runme}.

\subsection{Review and Verification at Agent Scale}
Review is shifting from reading diffs to checking intent and evidence. OpenAI reports that ``code review can quickly become the bottleneck'' as pull request volume grows, and that scoped review rules written in \texttt{AGENTS.md}, root-level for the repository and nested for services, raised recall of required findings from 58.3\% to 98\% in its evaluations; it advises keeping formatting and other mechanical checks in CI \cite{srikanth2026reviewrules}. Claude Code's review documentation treats instruction files in both directions: if a change makes a \texttt{CLAUDE.md} statement outdated, the reviewer flags that the docs need updating \cite{anthropic2026codereview}. GitHub's ReviewBench starts from the observation that ``No single reviewer, whether human or model, can identify everything worth finding in a pull request'' \cite{zhou2026reviewbench}, and GitHub recommends splitting large agent changes into reviewable stacks \cite{muiruri2026stack}.

Verification is moving past ``CI is green.'' Augment Code's verifier deploys each change, exercises it, and posts evidence rather than a verdict (``The Verifier never posts a pass-or-fail result''); it caught a fix wired to one endpoint but not its streaming twin while CI passed \cite{custer2026verifier}. Its review pipeline asks for ``inspectable proof rather than unsupported verdicts'' \cite{utture2026prmerge}. OpenAI's security agent records what it could not verify rather than implying it did (``If a reliable test can't be created safely, it records what remains unverified'') \cite{aiello2026daybreak}, and Anthropic's guidance for scheduled agents is to ``Report a failed read as unreadable, never as a quiet day'' \cite{martin2026automations}. Cursor extends verification past merge: a bot writes a monitoring plan before merge and compares production signals after deploy \cite{lalkaka2026rollouts}.

\subsection{Gates, Constraints, and Repository Skills}
Practitioners who no longer read agent code replace reading with enforcement. Martin overloads the test suite so that tampering is hard: ``It's not just one test they have to change. it's a lot of tests. And that makes it harder to change the tests'' \cite{martin2026overload}; and he has ``the agents write the tools that check the constraints. Those tools are deterministic'' \cite{martin2026tools}. Anthropic's Claude Code team runs tests, build, and lint before a pull request exists, ``Then a subagent reviews the diff with fresh context,'' and when the reviewer keeps flagging the same issue, ``we fix it at the source: in the skill, with a lint rule, or with updates to instructional files'' \cite{osmani2026codereview}. Claude Code's guidance describes a Stop hook that ``blocks the turn from ending until it passes'' and a fresh-context reviewer ``so the agent doing the work isn't the one grading it'' \cite{anthropic2026bestpractices}.

Both major harnesses now expose the hooks such gates need. Claude Code hooks can block a turn from ending, block a subagent from stopping, and deny a tool call or escalate it to a person before it runs \cite{anthropic2026hooks}. Codex hooks, generally available since May 2026, support the same blocking decisions for stopping and tool calls, but do not yet support escalating a tool call to a person, require project hooks to be trusted and reviewed, and are explicitly a ``useful guardrail, not a complete enforcement boundary'' \cite{openai2026codexhooks}.

The case for gates is that agents do not always report their own work faithfully. Transluce's analysis of real sessions found that, in around 2\% of sessions for each behavior, ``agents merge PRs to main without authorization, falsely claim approval from review agents, and reason that they shouldn't disable tests before quietly doing so anyway'' \cite{zhang2026misalignment}. Recent research frames the same risk directly: ``A coding agent can earn a passing grade by fixing its code, or by deleting the test that exposes the bug'' \cite{jiang2026hacktrace}. Tests written by the agent also need checking: Anthropic reports that at low effort an agent ``did not check that its new test would have caught the original bug'' \cite{shihipar2026effort}, and Antithesis applies mutation testing to agent-built test harnesses on the premise that ``a test is valuable if it fails when the software is modified to intentionally behave incorrectly'' \cite{padhye2026mutation}. Factory separates the acceptance instrument from the implementer entirely; its validator ``can expand the instrument \ldots\ but cannot weaken or revise it to accommodate what the candidate happens to contain'' \cite{factory2026large}.

Skills that encode these procedures are converging on one repository location. The Agent Skills documentation states that ``\texttt{.agents/skills/} paths have emerged as a widely-adopted convention for cross-client skill sharing'' \cite{agentskills2026clients}. Codex scans \texttt{.agents/skills} from the working directory up to the repository root \cite{openai2026codexskills}, and GitHub Copilot, Cursor, and Gemini CLI also read it \cite{github2026skills,cursor2026skills,google2026geminiskills}. Claude Code reads \texttt{.claude/skills/} and follows symlinked skill folders \cite{anthropic2026skills}, so one canonical folder plus a link serves both.

\subsection{Recent Independent Research}
Preprints from July 2026 onward corroborate the practitioner picture. Xu et al.\ find co-active agent pull requests in 40.2\% of the repositories they study, with textual conflict rates of 41.7\% for cross-agent pairs versus 19.8\% for same-agent pairs \cite{xu2026agentprs}. A follow-up finds that, in a stratified sample, 47.3\% of textual conflicts occurred even though the two pull requests authored disjoint file sets, because each diff is measured against its own base while the merge is checked against the common merge base; since exact local merge replay is cheap, it recommends simply verifying mergeability \cite{subramanian2026lineage}. NP-Bench observes that agents can each pass their own tests and still produce a broken merged result, and that partitioning work into declared scopes and ordering merges along producer-to-consumer dependencies raised clean integration from 1 of 9 to 9 of 9 scenarios, with a benefit that did not shrink for stronger models \cite{muku2026npbench}. Claim Plane finds that pre-write admission over declared change intents improves reliability, but mostly by serializing work, and fails when declared scopes are incomplete \cite{nikolaev2026claimplane}. CORVUS shows that agent trajectories accumulate stale file snapshots and that re-injecting current file contents reduces tokens while keeping pass rates comparable \cite{zheng2026corvus}. EA-Graph shows that anchoring verification claims to the artifacts they depend on improves judgments after upstream drift \cite{hsu2026eagraph}.

\subsection{Background: Work Before July 2026}
\label{sec:background}
The first draft drew on earlier work that remains useful context but carries less weight under the evidence policy. SWE-bench established real-world issue resolution as an agent benchmark \cite{jimenez2023swebench}; SWE-agent framed agents as a new kind of computer user that benefits from purpose-built interfaces \cite{yang2024sweagent}; and Agentless showed that simple localization, repair, and validation loops are competitive with complex autonomy \cite{xia2024agentless}. OpenAI's harness-engineering account introduced the idea of a short entry map into a versioned knowledge base, ``give Codex a map, not a 1,000-page instruction manual'' \cite{lopopolo2026harness}, an idea its September 2026 guidance reaffirms \cite{provencher2026astra}. Related work on codified context, spec-driven workflows, structured context, hierarchical skills, and token efficiency supported routed, partitioned, file-native knowledge \cite{vasilopoulos2026codified,taghavi2026speckit,mcmillan2026structured,sun2026corpus2skill,chen2026cuaskill,li2026singleagent,salim2026tokenomics,wang2026swepruner,voltagent2026awesome}.

Earlier multi-agent work anticipated the concurrency problem. Anthropic's parallel-agent compiler experiment coordinated agents through lock files committed under a \texttt{current\_tasks/} directory and Git synchronization, without an orchestrator \cite{carlini2026compiler}. CooperBench measured a ``curse of coordination'' between paired agents \cite{khatua2026cooperbench}; AgenticFlict catalogued merge conflicts in agent pull requests \cite{ogenrwot2026agenticflict}; and work on shared-workspace state management, cohesion-aware partitioning, and CRDT-based coordination explored alternatives to isolated worktrees \cite{liu2026storm,yang2026cocoder,pugachev2025codecrdt}. Early studies of agent pull request review found unreliable descriptions, little human review, and arguments that mandatory human review would not scale \cite{gong2026mci,duma2026reviews,monperrus2026endreview}. The recent evidence above is broadly consistent with these findings but was gathered on current agents at production scale.

\section{Problem Statement}
A repository that works for human experts can still be hostile to AI agents. Common failure modes include:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Context blindness}: the agent cannot find the relevant files, conventions, or prior decisions.
  \item \textbf{Instruction overload}: one large instruction file crowds out task context and makes priority unclear.
  \item \textbf{Architectural drift}: dependencies, naming, ownership, and layering are described but not checked.
  \item \textbf{Repeated rediscovery}: each session spends tokens re-learning the same layout and decisions.
  \item \textbf{Task overbreadth}: agents attempt broad refactors instead of completing one bounded change.
  \item \textbf{Verification friction}: tests, builds, linters, or acceptance checks are missing, slow, undocumented, or flaky.
  \item \textbf{Documentation rot}: docs are not versioned with the code or lack ownership and freshness checks.
  \item \textbf{Chat-memory dependency}: critical knowledge lives in conversations that future agents cannot access.
\end{enumerate}

Concurrent agent work adds five more:

\begin{enumerate}[leftmargin=*,resume]
  \item \textbf{Stale worldview}: an agent reasons from files, plans, or test results that other agents have already changed.
  \item \textbf{Invisible intent}: in-flight work lives in private branches and context windows, so agents cannot see or avoid each other's plans.
  \item \textbf{Semantic collision}: changes merge cleanly as text but break together, because each was verified only against its own base.
  \item \textbf{Contention hotspots}: shared files or operations that every task touches (one plan file, one changelog, one registry, one expensive build) serialize work and generate conflicts.
  \item \textbf{Unreviewable volume}: change volume exceeds human reading capacity, and change descriptions are not reliably tied to evidence.
\end{enumerate}

The design objective is not to maximize documentation volume. It is to maximize \emph{agent navigation quality}: the probability that an agent reads the right context, ignores irrelevant context, makes a bounded edit, and verifies the result. Under concurrency, the objective extends to \emph{integration quality}: the probability that many bounded edits, made in parallel, still compose.

\section{Definitions}
\textbf{Agent-legible repository.} A repository whose local artifacts let an AI coding agent understand what to do, where to look, which constraints apply, how to verify work, and how to update durable project memory.

\textbf{Entry map.} A short always-loaded file, often named \texttt{AGENTS.md}, \texttt{CLAUDE.md}, \texttt{GEMINI.md}, Cursor rules, Copilot instructions, or another tool-specific equivalent, that describes the repository purpose, workflow, key commands, gotchas, and pointers to deeper documents. The filename is less important than the role: the file is a maintained routing map into deeper context.

\textbf{Cold memory.} Versioned on-demand documents such as architecture docs, component design docs, product specs, security notes, and references.

\textbf{Hot memory.} Short high-priority operating rules that should be loaded every session: current task protocol, conventions, verification commands, and recovery steps.

\textbf{Component contract.} A design document for one component that records purpose, public API, implementation files, dependencies, tests, constraints, and non-goals.

\textbf{Execution plan.} A versioned task queue with checked tasks, acceptance criteria, decision log, and progress log.

\textbf{Verification harness.} The set of commands, tests, linters, scripts, probes, and acceptance checks that let an agent decide whether a change is complete.

\textbf{Concurrent repository.} A repository that multiple agents modify at overlapping times, so that any agent's view of the trunk can become stale during its own task.

\textbf{Work claim.} A visible, short-lived declaration that an agent is working on a task, with the scope it expects to touch (paths, interfaces, generated outputs), released when the work merges or is abandoned.

\textbf{Contention hotspot.} A file, interface, or operation that many unrelated tasks must change or trigger, such as a central registry, a single progress log, a hub module, a shared public contract, or a full rebuild.

\textbf{Intent record.} The short handoff attached to a change (commit message, pull request description, or plan entry) that says what the change is for, what it touched, what was checked, and what remains unverified.

\textbf{Integration verification.} Verification run against the change combined with the current trunk, as opposed to verification of the branch in isolation.

\textbf{Completion gate.} A harness hook that enforces the definition of done: it blocks an agent from finishing, or from opening a pull request, until required evidence and checks are present.

\textbf{Verification receipt.} The fixed fields an agent must end a code-changing task with: what was verified, what was not, which precedent was checked, and how confident the agent is and why.

\section{The Agent-Legible Repository Framework}
The framework consists of twelve mutually reinforcing artifacts. The first nine make a repository legible to one agent; the next two make it legible to many agents working at once; the last enforces the floor every agent must meet.

\subsection{Entry Map}
The entry map should be concise. It answers: What is this repo? What is the current workflow? What commands set it up and verify work? Where are architecture, conventions, design docs, active plans, and known issues? It should not duplicate every component detail; current frontier guidance is to keep it lightweight and spend its tokens on the codebase's gotchas \cite{shihipar2026context}, and to make it a router rather than a reading list that every edit must work through \cite{provencher2026astra}. In a concurrent repository it should also state the concurrency model in a few lines: that other agents may be editing, where in-flight work is visible, how to claim work, and how to verify against the current trunk.

\subsection{Knowledge Topology}
The repository needs an indexed knowledge base. A typical layout is:

\begin{verbatim}
AGENTS.md
ARCHITECTURE.md
CONVENTIONS.md
docs/
  design/
    index.md
    component-a.md
    component-b.md
  plans/
    active/          # one file per task; carries the work claim
    completed/
  decisions/         # one file per decision
  references/
  examples/
  QUALITY.md
  known-issues/      # one file per issue, or a generated index
src/
tests/
scripts/
\end{verbatim}

The index is critical. Without an index, many docs become an unsearchable pile. The agent should learn the reading path from the repository itself, and should be able to skip it for trivial edits.

The layout is also a concurrency decision. Knowledge that every task appends to (a single progress log, a single decisions file, a hand-maintained changelog) becomes a contention hotspot when many agents run at once. Prefer one file per plan, decision, issue, or change note, and generate indices and changelogs from those files with a script instead of editing them by hand. Small, separately owned files merge cleanly; one shared file does not.

\subsection{Component Contracts}
Each major component should have one component design document. For example, a systems repository might have \texttt{docs/design/loader.md}, \texttt{docs/design/memory-reader.md}, and \texttt{docs/design/overlay.md}; a web service might have \texttt{docs/design/auth.md}, \texttt{docs/design/billing.md}, and \texttt{docs/design/api.md}. These files are not ordinary explanatory docs. They are context routers. When an agent is asked to work on a component, it should read that component's design doc first instead of scanning the whole repository.

Each component contract should include purpose, allowed dependencies, public API, implementation files, test files, constraints, acceptance criteria, and explicit non-goals. This localizes context. If the task is about the billing adapter, the agent should not need to understand every renderer, database adapter, or deployment script. If a component has no design doc, the agent should treat that as missing harness infrastructure and either create a minimal contract or record the gap before doing broad work.

Under concurrency, component contracts are also coordination boundaries. Current practice splits parallel tasks along file and component boundaries and merges them in dependency order \cite{osmani2026cloud,anthropic2026migrations}. A contract that names the paths a component owns, the consumers of its public API, and the hub files it shares makes that split mechanical. A change to a public contract is a producer-to-consumer event: it should be scheduled and merged before dependent work, not discovered at merge time \cite{muku2026npbench}.

\subsection{Active Execution Plans}
Large work should be decomposed into checkable tasks. The plan should identify the next unchecked item, define acceptance criteria, and require the agent to update progress only after verification. This converts vague intent into an executable queue. With many agents, keep one plan per task or workstream rather than one shared plan that every agent edits, and keep queues on disk so that interrupted runs can resume \cite{anthropic2026migrations}.

\subsection{Mechanical Invariants}
Documentation alone is weak. Important rules should become mechanical checks: dependency boundaries, naming conventions, public API documentation, file size limits, schema validity, generated-code freshness, forbidden imports, and required tests. Lint errors should include remediation guidance because their output becomes agent context.

Mechanical invariants are also how human judgment scales across concurrent agents. When an engineer has to tell an agent ``no'' because it violated a system constraint \cite{anthropic2026scion}, that refusal should be encoded once, as a lint, test, contract non-goal, or anti-pattern, so that the next ten agents do not need to hear it again. Current practice does exactly this: Cursor's coordinator adds a lint rule when it sees the same mistake twice \cite{cursor2026projects}, and Anthropic's migration rulebook grows while ``the code never gets hand-patched against it'' \cite{anthropic2026migrations}.

Structural quality budgets belong here too. Humans may no longer read the code, but agents do, and messy code slows them down \cite{martin2026messy}. Bound function size, complexity, duplication, and coverage mechanically, so that agents cannot create the tangles they later fail to untangle.

\subsection{Verification Harness}
Every repository should expose a small set of commands for setup, build, test, lint, typecheck, formatting, and domain-specific acceptance. The commands should be listed exactly in the entry map so agents do not infer them \cite{deoliveira2026verification}; agents running in fresh cloud environments only know what the repository says \cite{osmani2026cloud}, and a documented one-line setup command is a basic readiness criterion \cite{factory2026sandboxes}. Commands should be cheap enough to run frequently, and their output short and greppable because it becomes agent context. Where a task is large, define an executable standard of completion before implementation starts, so that the definition of done cannot quietly shrink to whatever was built \cite{factory2026large}.

\subsection{Quality and Entropy Ledger}
A quality ledger records component trust levels, test gaps, known risks, and last-updated dates. A known-issues file records non-blocking defects. These files prevent agents from treating all parts of the codebase as equally reliable.

\subsection{Examples and Anti-Patterns}
Agents imitate local examples. Repositories should include gold-standard examples and explicit anti-patterns for common mistakes. When a recurring failure appears, either add a test/lint or document it as an anti-pattern with a replacement pattern.

\subsection{Skill Layer}
The repository should have reusable skills for repeated workflows: adding a component, writing a design doc, performing a code review, verifying a change, debugging a failing test, creating a migration, or auditing documentation. Skills should be specific, with short descriptions and a root file that routes to supporting docs and scripts \cite{provencher2026astra}. A flat list of dozens of similar skills creates selection burden. Shared verification and review skills turn personal checks into team infrastructure \cite{deoliveira2026verification}.

Keep repository skills in \texttt{.agents/skills/<name>/SKILL.md}, the emerging cross-tool location \cite{agentskills2026clients,openai2026codexskills}, and link \texttt{.claude/skills/<name>} to the same folder for Claude Code \cite{anthropic2026skills}. Give each skill the standard \texttt{name} and \texttt{description} frontmatter, and keep tool-specific metadata in sidecar files. Checked-in skills can change what agents are allowed to do, so review them like code.

\subsection{Coordination Surface}
A concurrent repository needs one visible place where in-flight work is declared. If all agents share a harness with a task list and file-locked claiming, or a coordinator that assigns work, use it \cite{anthropic2026agentteams,cursor2026projects,openai2026agentsapi}. If agents share only the repository, commit a small claim file per task, for example the header of the task's file in \texttt{docs/plans/active/}, stating the task, the claiming session, the expected scope (paths, public interfaces, generated outputs), and when it started. Pushing a new claim to the trunk is an atomic test: if another agent already claimed the task, the push fails and the second agent picks other work, a pattern used in earlier parallel-agent experiments \cite{carlini2026compiler}. Shared context files that agents add to as they learn serve the same role for knowledge that claims serve for work \cite{cursor2026projects}.

Claims are coordination hints, not locks on the whole repository. They let agents avoid duplicate work and predictable collisions, and they make intent visible to the next agent. They should be amended when scope grows and removed when the work merges or is abandoned. Overly broad or incomplete claims either serialize everything or fail closed \cite{nikolaev2026claimplane}. The same applies to expensive shared operations: route a full rebuild or similar step through one owner instead of letting every agent trigger it \cite{anthropic2026migrations}.

\subsection{Intent Records}
Every merged change should carry a short intent record: what the change is for, which component and contract it touches, what it deliberately does not do, what was checked, and what remains unverified. This matches current frontier guidance that agents end work with ``a short handoff covering what changed, what was checked, and what still needs attention'' \cite{openai2026gpt6guide}. Intent records are the surface that humans review when they no longer read every line \cite{anthropic2026scion}, and the surface that later agents read to understand why the code is the way it is \cite{lewi2026runme}. They should point to evidence a machine or reviewer can re-check (test names, command output, CI runs, traces) rather than narrative verdicts \cite{utture2026prmerge,custer2026verifier}, and say plainly what could not be verified \cite{aiello2026daybreak,martin2026automations}.

\subsection{Completion Gate}
Instructions ask; gates enforce. A completion gate is a hook in the agent harness that turns the definition of done into something an agent cannot skip. At the end of a turn it checks that an agent which changed files has written a verification receipt. Before a pull request is created it runs the repository's full verification and escalates changes to protected acceptance specs to a person. Section~\ref{sec:gates} describes what a gate should check and where each check belongs.

\section{Designing for Concurrent Agents}
\subsection{Three Layers of Concurrency Control}
Coordination among concurrent agents is not one problem owned by one tool. It is split across three layers, and a repository designer should know which layer owns which part.

\begin{table}[h]
\centering
\small
\begin{tabularx}{\textwidth}{l L L}
\toprule
Layer & Owns & Examples \\
\midrule
Repository & Durable, versioned coordination knowledge: boundaries, contracts, claims, intent records, invariants, and verification commands. & Component contracts with owned paths; per-task plan files; generated indices; lints; integration checks. \\
Harness & Live, session-level coordination: isolation, task assignment, messaging, permissions, and completion gates. & Worktrees or cloud machines per agent; coordinators and subagents; shared task lists; cross-session messages \cite{osmani2026cloud,anthropic2026crosssession,cursor2026projects,openai2026agentsapi}. \\
Source control and forge & Storage, history, merging, review, CI, and deployment of changes at scale. & Server-side merges, cheap commits, reference-update throughput, test selection, review rules, post-merge and post-deploy checks \cite{anthropic2026scion,celenza2026gitinfra,malhotra2026ci,lalkaka2026rollouts}. \\
\bottomrule
\end{tabularx}
\caption{Where concurrency problems are solved. This paper addresses the repository layer and assumes the other two.}
\end{table}

For most teams, the honest assessment is that the source-control and CI layer is a real bottleneck at high agent counts and is being rebuilt by frontier labs and forges, that the harness layer is improving quickly and absorbs much of the live coordination, and that the repository layer is the one a team fully controls today. The repository layer is also the only one that survives a change of harness or model; as OpenAI notes, repository instructions also guide other contributors' agents, which may run on different models \cite{provencher2026astra}.

\subsection{What Git Does and Does Not Give Concurrent Agents}
Git gives every agent an isolated, complete, cheap-to-branch snapshot and a reliable three-way merge. Those are real strengths: isolation prevents agents from overwriting each other mid-task, and pushing to a shared trunk is an atomic compare-and-swap that can arbitrate simple claims.

Git does not give agents awareness. A branch hides in-flight intent until it is pushed and merged, so isolated agents duplicate each other's fixes \cite{osmani2026cloud}. A clone or worktree is stale from the moment it is created, and longer agent sessions make it staler \cite{segner2026longsessions}. A clean textual merge says nothing about semantic compatibility, and conflicts can arise even when two changes authored disjoint files \cite{subramanian2026lineage}. All merges contend on one trunk reference \cite{celenza2026gitinfra}, and global serialization through a merge queue does not keep up at agent scale \cite{anthropic2026scion}. The design rules below compensate for these gaps without replacing Git.

\subsection{Design Rules}
\begin{enumerate}[leftmargin=*]
  \item \textbf{Assume a moving trunk.} Tell agents in the entry map that the repository is concurrent. Agents should re-read a file before editing it if time has passed, re-sync before declaring work done, and treat earlier test results as stale once the trunk moves \cite{zheng2026corvus,hsu2026eagraph}.
  \item \textbf{Declare scope before writing.} Every nontrivial task gets a claim with expected scope. Agents check existing claims before starting and amend their own when scope grows.
  \item \textbf{Partition along components, and schedule shared changes.} Split parallel work along component and file boundaries. Identify hub files and shared public contracts explicitly; changes to them are scheduled, merged first, and announced, because they are where parallel work collides \cite{osmani2026cloud,muku2026npbench}. Route expensive shared operations through one owner \cite{anthropic2026migrations}.
  \item \textbf{Shard shared knowledge.} Replace append-everywhere files with one file per plan, decision, issue, or change note. Generate indices, registries, and changelogs by script. Regenerate lockfiles and generated code with project tooling instead of merging them by hand.
  \item \textbf{Keep changes small and reviewable.} Small changes that integrate often have less time to go stale and smaller conflict surfaces. Split large agent changes into ordered stacks \cite{muiruri2026stack}.
  \item \textbf{Verify the integrated result.} A branch that passes its own tests is not done. Replay the merge against the current trunk (local merge replay is cheap \cite{subramanian2026lineage}), re-run affected verification, and rely on post-merge, pre-deploy, and post-deploy checks to catch semantic collisions that no pre-merge gate will see \cite{anthropic2026scion,muku2026npbench,lalkaka2026rollouts}.
  \item \textbf{Review intent and evidence, and route attention by risk.} Require intent records. Put scoped review rules in the instruction files reviewers read, keep mechanical checks in CI \cite{srikanth2026reviewrules}, and use path-based ownership or approval rules to separate low-risk changes (comments, docs, tests) from sensitive ones (public contracts, security boundaries, migrations, merges to main, deploys) so that scarce human attention goes where it matters \cite{anthropic2026scion,anthropic2026block}.
  \item \textbf{Fix the process, not the output.} When a human or reviewing agent rejects a pattern, encode the rejection as a lint, test, contract non-goal, rule, or anti-pattern so it applies to all concurrent agents \cite{anthropic2026migrations,cursor2026projects}. When a change makes instruction files outdated, update them in the same change \cite{anthropic2026codereview}.
\end{enumerate}

\subsection{What Not To Do}
Do not build a version control system unless the repository is genuinely at the scale where storage, transfer, and reference updates dominate; the organizations that have done so are frontier labs and forges serving enormous agent load \cite{anthropic2026scion,celenza2026gitinfra,marti2026gitscale}. Do not try to solve coordination by serializing everything through one lock, one plan file, or one merge queue; that recovers correctness by giving up the parallelism that motivated running many agents \cite{nikolaev2026claimplane}. Do not over-engineer the setup either: simple, clear instructions have outperformed elaborate ones in parallel migrations \cite{openai2026asana}. And do not let agents coordinate only through transient chat; current harnesses converge on durable shared state such as task lists, shared context files, and on-disk queues \cite{anthropic2026agentteams,cursor2026projects,anthropic2026migrations}. Prefer durable, structured, verifiable state: claims, contracts, intent records, and checks.

\section{Gates: Constraints Instead of Reading}
\label{sec:gates}
When people stop reading code, the constraints around the code become the review. This section describes how to build them so that they hold under many concurrent agents.

\subsection{Layers of Enforcement}
Each constraint should live at the cheapest layer that can enforce it, and the important ones should be repeated at a layer the agent cannot reach.

\begin{table}[h]
\centering
\small
\begin{tabularx}{\textwidth}{l L L}
\toprule
Layer & Strength & Holds \\
\midrule
Instructions & Advisory; read every session & Commands, gotchas, routing, the receipt format \\
Skills & Procedure; loaded on demand & How to reproduce, verify, check precedent, and finish \\
Hooks & Enforced in the harness; per tool & End-of-turn receipt; pre-pull-request checks; escalation of protected changes and merges \\
CI and branch protection & Enforced on the server & The full check suite; required approvals; protected paths \\
Post-merge and deploy & Enforced on the result & Semantic collisions; production signals \\
\bottomrule
\end{tabularx}
\caption{Layers of enforcement. Hooks catch shortcuts early; CI is the boundary an agent cannot route around.}
\end{table}

Hooks are fast feedback, not a security boundary: an agent with shell access can sometimes avoid them, and Codex documents its tool hooks as a guardrail rather than complete enforcement \cite{openai2026codexhooks}. CI, branch protection, and required approvals remain the hard boundary.

\subsection{What a Gate Checks}
\begin{enumerate}[leftmargin=*]
  \item \textbf{Only this agent's changes.} Record a baseline (commit and pre-existing uncommitted files) when a session or subagent starts, and judge only what changed since. Compare the whole tree, not just the files touched through edit tools, so edits made through shell commands and commits count. Key the baseline by session and subagent so concurrent agents do not share it.
  \item \textbf{A verification receipt.} An agent that changed files must end with \texttt{VERIFIED}, \texttt{UNVERIFIED}, \texttt{PRECEDENT}, and \texttt{CONFIDENCE} fields. The receipt must always be satisfiable honestly: an agent that could not run a check says so under \texttt{UNVERIFIED}. A gate that can only be passed by succeeding creates pressure to fabricate.
  \item \textbf{The full check before a pull request.} Creating a pull request runs the repository's own verification command first and is denied if it fails. Words cannot satisfy this check.
  \item \textbf{Protected acceptance specs.} Human-approved acceptance tests and Gherkin scenarios are the part of the system people still read. Changes to them escalate to a person, so an agent cannot weaken the standard it is measured against \cite{factory2026large}.
  \item \textbf{Tests that bite.} A new test should be seen failing before the fix passes it; mutation testing checks that tests fail when behavior is broken; many overlapping tests make tampering costly \cite{shihipar2026effort,padhye2026mutation,martin2026overload}.
  \item \textbf{Structural budgets.} Function size, complexity, duplication, and coverage limits keep the code navigable for the agents that maintain it \cite{martin2026messy}.
  \item \textbf{Precedent.} Before deleting or redesigning existing behavior, the agent checks the history and pull request that introduced it, and treats unexplained guards, timeouts, and retries as intentional until history says otherwise. This is the mechanical form of a human engineer saying ``no'' \cite{anthropic2026scion}.
  \item \textbf{No bypass.} Deleting assertions, skipping tests, raising timeouts, weakening types or validation, and editing the gate itself are forbidden without explicit human approval, and merges and deploys stay with people \cite{anthropic2026block}.
  \item \textbf{A fresh reviewer.} For nontrivial changes, a reviewer in a fresh context sees only the final diff, the acceptance behavior, and the evidence \cite{osmani2026codereview,anthropic2026bestpractices}.
  \item \textbf{Fail closed.} If the gate itself errors, it blocks.
\end{enumerate}

\subsection{Personal and Repository Gates}
Experienced practitioners shape their own harnesses and keep tuning them. A gate therefore has two owners. The repository owns what is true for every contributor: exact commands, protected paths, the receipt format, and CI. A person may add a stricter personal gate on top, with repository-specific variants that route to each repository's commands, but it should never override the repository's own instructions. The repository's job is to make any gate easy to plug in: if the commands, protected paths, and receipt format are written down, a personal or team gate can enforce them without guessing.

In a test of the template that accompanies this paper, a headless Claude Code session asked to edit a file and reply only ``done'' was blocked until it produced a receipt, and the receipt recorded that it had not been able to run the program. A request to open a pull request while the configured check failed was denied before the command ran. This is a demonstration, not evidence of effectiveness at scale.

\section{Operational Method}
\subsection{Greenfield Setup}
For a new repository, create the harness before the code grows:

\begin{enumerate}[leftmargin=*]
  \item Write a short agent entry file, such as \texttt{AGENTS.md} or a tool-specific equivalent, with purpose, exact setup and verification commands, gotchas, document map, and concurrency model.
  \item Define architecture layers and dependency rules in \texttt{ARCHITECTURE.md}.
  \item Define coding conventions and error-handling patterns in \texttt{CONVENTIONS.md}.
  \item Create \texttt{docs/design/index.md} before writing many component docs.
  \item For each major component, write one component design doc before or alongside implementation, including owned paths and consumers of its public API.
  \item Add tests and scripts as soon as public APIs exist, including a one-line setup command and a command that verifies a branch against the current trunk.
  \item Use one plan file per task in \texttt{docs/plans/active/}, with a claim header, and require one-task-at-a-time execution per agent.
  \item Track quality, known issues, and decisions in versioned files, one entry per file where many agents will write.
  \item Define the intent-record format and scoped review rules.
  \item Install a completion gate: a receipt at the end of each turn, the full check before pull requests, and protected acceptance specs. Put skills in \texttt{.agents/skills/}.
\end{enumerate}

\subsection{Brownfield Repair}
For an existing repository, do not begin by documenting everything. Begin by reducing agent uncertainty:

\begin{enumerate}[leftmargin=*]
  \item Inventory components and current setup and verification commands.
  \item Create or repair the entry map.
  \item Create an architecture map from actual imports and build targets.
  \item Create a design index with statuses: complete, in progress, stale, missing.
  \item Write component contracts only for high-change, high-risk, or frequently edited areas first.
  \item Add scripts for the commands humans already run manually.
  \item Add mechanical checks for the most damaging recurring mistakes.
  \item Create a quality ledger and known-issues file.
  \item If several agents already work in the repository, find the contention hotspots (files most often involved in conflicts or touched by unrelated changes, and expensive shared operations) and shard, generate, schedule, or serialize them first.
  \item Add a completion gate once verification commands exist, starting with the receipt and the pre-pull-request check.
\end{enumerate}

\subsection{Default Agent Protocol}
A future coding agent should follow this loop, scaling the reading steps to the size of the task; a typo fix does not need the full reading path \cite{provencher2026astra}:

\begin{enumerate}[leftmargin=*]
  \item Sync with the current trunk.
  \item Read the entry map.
  \item Read the active plan or issue, and check existing claims for overlapping work.
  \item Identify the component and read its design contract.
  \item Claim the task with its expected scope, unless the harness already assigned it.
  \item Read architecture and conventions relevant to the change.
  \item Inspect existing code and tests in the target component.
  \item Make the smallest change satisfying the task. Re-read any file before editing it if others may have changed it.
  \item Run the documented verification commands.
  \item Re-sync with the trunk, resolve conflicts, and re-run affected verification on the integrated result.
  \item Write the intent record and end with the verification receipt; update docs, plan, quality ledger, or known issues only when the result changes durable project knowledge.
  \item Before opening a pull request, run the full check; expect the gate to deny the request if it fails.
  \item Release the claim and stop after the requested task is complete.
\end{enumerate}

\section{Evaluation Metrics}
Agent-legibility can be evaluated empirically. Useful metrics include:

\begin{itemize}[leftmargin=*]
  \item \textbf{Context localization}: files opened before first correct edit; irrelevant files opened per task.
  \item \textbf{Token efficiency}: input tokens before first edit; total tokens to green verification.
  \item \textbf{Task success}: percentage of tasks completed without human clarification.
  \item \textbf{Verification success}: first-run build/test pass rate after edit; time-to-green.
  \item \textbf{Architectural coherence}: number of dependency or convention violations per task.
  \item \textbf{Recovery}: ability to resume from a fresh session or fresh cloud environment using only repository-local state.
  \item \textbf{Documentation freshness}: stale links, stale file references, and docs contradicted by code.
  \item \textbf{Mistake recurrence}: repeated failures before and after adding docs, lints, or scripts.
\end{itemize}

For concurrent repositories, add:

\begin{itemize}[leftmargin=*]
  \item \textbf{Conflict rate}: share of changes that conflict with the trunk at integration time, and which files cause them.
  \item \textbf{Semantic breakage}: post-merge or post-deploy failures in changes that each passed pre-merge verification.
  \item \textbf{Duplicate and overlapping work}: tasks attempted by more than one agent, or claims with overlapping scope.
  \item \textbf{Serialization ratio}: share of work that had to wait on another agent; parallel speedup relative to one agent.
  \item \textbf{Intent fidelity}: share of intent records whose claims match the diff and the cited evidence.
  \item \textbf{Human attention}: share of changes that required human review, and whether that share tracks risk.
\end{itemize}

For gated repositories, add:

\begin{itemize}[leftmargin=*]
  \item \textbf{Gate pass rate}: share of turns and pull requests that pass the gate on the first attempt.
  \item \textbf{Escaped defects}: failures after merge in changes that passed the gate.
  \item \textbf{Tampering}: attempts to edit tests, assertions, protected specs, or the gate itself.
  \item \textbf{Test strength}: mutation score of agent-written tests.
  \item \textbf{Receipt fidelity}: share of receipts whose \texttt{VERIFIED} claims match what actually ran.
\end{itemize}

A practical experiment is to run the same set of coding tasks against two versions of a repository: baseline and agent-legible. Compare task success, tokens, files opened, verification failures, and human interventions. For concurrency, run the same task set with one agent and with several agents in parallel, and compare integrated success, conflicts, and wall-clock time.

\section{Limitations}
The framework is model-dependent. A structure that works well for frontier coding agents may be insufficient for smaller models, and current guidance for frontier models already favors less instruction text than earlier models needed \cite{shihipar2026context}. Documentation can also become a liability if stale, too broad, or not connected to mechanical checks. Small prototypes may not need the full framework. Some domains require additional artifacts, such as threat models, product specs, data schemas, migration guides, or UI design systems. Finally, this paper is a framework and working synthesis; formal validation requires controlled experiments across repositories, models, and task types.

The evidence policy carries its own limits. Weighting recent first-party reports puts the argument on sources that are not peer reviewed, whose metrics are self-reported, and whose authors sell the products they describe. Several of the strongest numbers come from a few organizations operating at unusual scale. Recent preprints often use self-built benchmarks. The paper will also age quickly; its sources should be re-weighted at each revision.

The concurrency guidance carries additional caveats. Claims can become their own bottleneck if they are too coarse, and incomplete claims can block legitimate work. Harness capabilities for coordination are changing quickly, so a repository should depend on the repository-layer conventions here rather than on any one harness feature. Finally, reviewing intent instead of code is only as safe as the evidence behind the intent; it depends on strong verification and post-merge checks.

Gates have limits of their own. A receipt check verifies that the fields are present, not that they are true; CI and fresh reviewers must still check the claims. Hooks are harness-specific, change quickly, and can sometimes be avoided by an agent with shell access. Slow gates tax every turn, so the end-of-turn gate should stay cheap and expensive checks belong before pull requests and in CI. And no first-party study yet measures how much gates reduce escaped defects; the evidence here is practitioner reports and demonstrations.

\section{Conclusion}
AI-native software development changes the role of repository design. The repository is no longer only storage for code; it is the agent's perception layer, memory system, task board, rulebook, and feedback environment. It is also, increasingly, a shared workspace that many agents change at once and that humans steer through intent and evidence rather than through reading code. Agent-legible repositories reduce wasted context, constrain implementation, preserve project memory, make verification routine, and make concurrent work visible. The core prescription is simple: give agents a map, make knowledge navigable, enforce what matters mechanically, declare work before doing it, verify the integrated result, gate completion on evidence, and fix the process whenever it produces a recurring failure.

\section{Minimal Claim and Intent Record Templates}
A claim, placed at the top of a task file in \texttt{docs/plans/active/} or kept in the harness task list:

\begin{verbatim}
---
task: <short task name>
claimed-by: <agent or session identifier>
started: <date and time>
scope:
  paths: [<paths this task expects to change>]
  interfaces: [<public APIs or contracts it may change>]
  generated: [<generated outputs it will regenerate>]
status: claimed | in-review | merged | abandoned
---
